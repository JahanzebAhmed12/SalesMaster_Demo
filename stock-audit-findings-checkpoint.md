# Stock consistency audit checkpoint

Read-only source audit; no transaction endpoints or database writes executed.

## Confirmed source findings

1. **Current stock is a mutable snapshot, not the Stock Check result.** `/api/stock/current` returns `RegularProduct.current_stock` and `NonProduct.current_stock` directly. Stock Check computes `opening_stock + purchases - positive finalized sales + completed customer returns - dumps - supplier returns`, then compares the result to a `ClosingStock` row (or zero when none exists). It does not compare to product.current_stock.

2. **Closing Stock directly overwrites live current_stock.** POST `/api/closing-stock` assigns `product.current_stock = submitted quantity` for both first and subsequent saves, and adds a `closing_stock_adjustment` movement. This can intentionally or accidentally reset live stock to a historical/manual quantity. Frontend displays the same live current_stock next to the closing quantity and permits historical dates subject to permission.

3. **Closing-stock delete cannot find the movement created by closing-stock save.** Save creates `StockMovement(reference_id=None, reference_type='closing_stock')`; delete searches for `reference_id == closing_stock.id`. Therefore the created adjustment is not found/reversed and the overwritten current_stock is not restored. Delete only removes the ClosingStock row (and leaves the live snapshot changed).

4. **Customer-return status transitions can apply stock incorrectly.** Create adds stock only for status `completed`; `approve` adds stock for any pending return; `complete` only changes status and does not add stock. `update_customer_return` adjusts stock whenever quantity changes regardless of old/new status. `reject` subtracts stock even though a pending create did not add it. Delete always subtracts quantity regardless of status. Examples: pending->rejected produces an unwanted negative delta; pending create->edit quantity->approve can double count; completed/rejected deletion can reverse the wrong amount.

5. **Supplier-return status transitions can double-apply or leave incorrect stock.** Create always subtracts stock regardless of status; `approve` subtracts again; `reject` adds one quantity back; `complete` only changes status. Update changes stock for quantity differences regardless of status. Delete always adds quantity back regardless of status. A pending return created then approved nets -2q; pending created then rejected nets 0; rejected then deleted adds q although no net effect should remain.

6. **Sale delete/cancellation ledger scope misses negative-sale return movements.** Negative sale items create positive `customer_return` movements and a CustomerReturn entity; sale-create later relinks those movements from reference `(sale, sale.id)` to `(customer_return, customer_return.id)`. Sale update/delete reconciliation queries only movements whose `reference_type == 'sale'`, so relinked negative-sale movements are excluded. Sale delete also deletes CustomerReturn entities but does not reverse their stock movement. This leaves current_stock too high after a negative-line sale is deleted/cancelled, while Stock Check no longer counts the deleted CustomerReturn.

7. **Sale-update relink/recreation is fragile and must be traced with exact code/data.** Finalized sale update deletes all CustomerReturn rows for the sale before rebuilding; the source currently shown relinks negative-sale movements created in the same request, but stale/relinked movements from previous versions may not be found by the update's `reference_type='sale'` query. This can leave orphaned movements or missing return movements after repeated edits.

8. **Concurrency risk is material on SQLite.** `update_product_stock` reads `product.current_stock`, computes a new value, assigns it, then inserts a movement. It calls `with_for_update()`, but SQLite does not provide row-level `FOR UPDATE` locking. The configured SQLite engine uses `check_same_thread=False` and timeout/retry handling for locked errors. Concurrent requests can read the same old value and last-writer-wins, while both movements remain; movement previous/new snapshots can expose this. Stock Check reads entity tables and can remain mathematically consistent while the stored snapshot loses one or more concurrent deltas.

9. **Purchase invoice create commits its header before item/stock processing.** If an item or stock update fails, rollback cannot undo the already committed PurchaseInvoice header, potentially leaving an orphan invoice. Item loops do apply each line, including repeated product lines, and update/delete reverse each line; duplicate lines are therefore net-correct in the normal serialized case but vulnerable to partial failures/concurrency. Product type is inferred by checking regular first, then non, so identical numeric IDs across the two tables would be misclassified if such IDs exist.

10. **Stock Check date/source semantics are inconsistent with movement chronology.** Purchases use `StockMovement.movement_date` with created_at fallback only for NULL. Sales and return/dump entity rows use their business/date fields. Opening stock looks backward only up to seven days and treats any date with at least one ClosingStock row as active, returning zero for omitted products on that day. Supplier returns are counted regardless of status. Dumps are counted regardless of status. Customer returns count only `completed` rows. These rules differ from the mutation routes and can create end-of-day differences.

11. **Historical closing calculation uses `StockMovement.created_at`, not `movement_date`, and selects latest movement.new_stock.** Backdated transactions created later can be absent from the historical closing response; closing overrides/backdated writes can also make the latest movement snapshot diverge from entity-based Stock Check.

12. **On-hold invoices are frontend/localStorage reservations only.** `heldInvoices` are stored in browser localStorage and subtracted from availability for new invoices. They do not write Product.current_stock, StockMovement, or a server-side reservation. Holds are not shared across users/devices. Edit mode adds back original saved quantity but does not subtract held-invoice reservations, so availability can differ by mode and concurrent users can oversell; this alone does not create a ledger mismatch unless resulting transaction writes race/fail.

## Reproducible isolated evidence

- The committed `backend/test_stock_system.py` was run only against a new temporary SQLite database, never the working database. It completed 79/79 checks, but its Stock Check helper is ledger-based while production `app.py` Stock Check reads entity tables for sales/returns/dumps/supplier returns. Therefore the passing harness does not validate production report semantics.
- A read-only call to the production `/api/reports/stock-check` route against that isolated scenario for 2026-06-02 showed Test Product A: `os=93`, `ns=150`, `sales=10`, `crtn=0`, calculated `stock=233`, `clStock=236`, `extra 3`; this reflects the harness's negative sale not creating a CustomerReturn entity, and proves the test harness and production report are not equivalent.
- An isolated concurrency probe ran 16 threads x 20 stock-helper increments (320 successful calls) on SQLite. It produced `current_stock=58`, `movement_rows=320`, and movement quantity sum `320`, with no lock failures. This is direct evidence of lost updates under concurrent read-modify-write despite `with_for_update()`: 262 units were lost from the stored snapshot while all movements remained. This is a critical root cause for multi-user divergence.
- The admin cleanup helper is another direct writer: `cleanup_sale_stock_movements` removes duplicate sale movements and directly subtracts their quantities from `product.current_stock`. It only scopes `reference_type='sale'`, so relinked negative-sale return movements are outside its cleanup scope; its direct correction can itself be wrong if the snapshot is already inconsistent.

## Additional reproducible and structural findings

- Isolated route reproduction of customer returns starting at stock 100 showed `pending` create left stock at 100, but `reject` changed it to 95 and subsequent delete changed it to 90. The expected stock remained 100. A second pending return quantity edit from 5 to 7 failed with HTTP 500 (`float` minus `decimal.Decimal`), so the status/quantity change was not applied; approval then added only the original 5. This confirms both wrong status reversal and a reachable numeric-type bug.
- The same isolated reproduction showed supplier return create with status `pending` reduced stock immediately, approval reduced it again, rejection restored one quantity, and deletion then added quantity again. The movement list for one rejected supplier return contained `supplier_return -4`, `supplier_return_rejection +4`, and `supplier_return_cancellation +4`, proving deletion reverses a return that had already been rejected.
- Legacy `/api/stock/customer-return`, `/api/stock/dump`, and `/api/stock/supplier-return` routes call the central helper but do not commit. In an isolated route probe they returned new-stock values 103, 98, and 104, but after request teardown the product remained at 100 while three movement rows persisted and no corresponding CustomerReturn, DumpEntry, or SupplierReturn rows existed. These endpoints are not referenced by the current frontend, but if called by another client/integration they can directly create Stock Check invisibility and snapshot/ledger divergence.
- PurchaseInvoiceItem stores only `product_id`, with no product-type field or foreign-key discriminator. The purchase frontend keeps type in a UI-only `regular-<id>`/`non-<id>` selection key, then serializes items as `{productId, productName, quantity, ...}`. Backend create/update/delete checks `RegularProduct.query.get(id)` first and otherwise `NonProduct`, so if regular and non-product tables both contain ID 1 (normal because they have independent sequences), a non-product purchase with ID 1 is applied to the regular product. This is a high-severity product identity risk.
- The normal customer-return frontend always posts status `completed` and exposes create/delete only; the normal supplier-return frontend defaults to `completed`, forcibly resets edited records to `completed`, and exposes CRUD rather than approval. Thus the status-transition bugs are directly reachable by API/admin/integration calls, while ordinary UI use still exercises completed-return create/update/delete paths. Completed-return delete currently reverses quantity unconditionally, which is correct only for a return that actually affected stock; the backend does not derive that fact from status/movement state.

## Frontend freshness findings

- Sales create/update uses the shared sales invalidation hook, invalidating `currentStock` and report queries, and broadcasts invoice events via `BroadcastChannel('sales-updates')`. Purchase create/update/delete explicitly invalidates `currentStock` and Stock Check queries and broadcasts `STOCK_UPDATED`.
- Customer-return create/delete only refetch the return list. Dump create/delete only refetch the dump list. Supplier-return create/update only update the supplier-return query cache, and delete invalidates only supplier-return queries. None of these normal flows invalidate `currentStock` or `stock-check`, nor do they broadcast a stock event. An already-open sales-entry or closing-stock page can therefore continue showing stale stored stock after a return or dump, even when the backend write succeeded.
- The broadcast mechanism is browser-profile/tab-local, not server-wide. It cannot synchronize separate users/devices. Sales-entry availability is also calculated client-side from stored `/api/stock/current` plus unsaved line quantities and browser-local held invoices; it is not an authoritative reservation check.
- Purchase frontend product selection tracks regular/non type in a prefixed local key, but `items` stores only numeric `productId` and `productName` before save. The backend consequently cannot reliably identify non-products when numeric IDs overlap across the independent product tables.
