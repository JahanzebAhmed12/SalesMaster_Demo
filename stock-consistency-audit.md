# SalesMasterDashboard Stock-Consistency Audit

**Prepared by:** Manus AI  
**Scope:** Read-only end-to-end review of frontend, Flask backend, stock movement paths, invoice edits, duplicate lines, holds, returns, dumps, purchases, supplier returns, closing stock, and concurrency.  
**Repository:** `JahanzebAhmed12/SalesMasterDashboard`  
**Audit status:** Findings only. No stock behavior, transaction, or production database data was changed.

## Executive conclusion

The divergence is not caused by one arithmetic mistake. The application currently maintains **two different stock models**: a mutable `product.current_stock` snapshot updated by a central helper, and a Stock Check report reconstructed from a mixture of closing-stock rows, purchase movements, and transaction entity tables. Those models are not guaranteed to receive the same events, use the same statuses, use the same dates, or execute atomically.

The most strongly evidenced root cause is **concurrent lost updates on SQLite**. The helper reads `current_stock`, calculates a new value, writes it, and records a movement. It requests `with_for_update()`, but SQLite does not provide the row-level lock semantics that this code expects. In an isolated reproduction with 320 concurrent `+1` updates, all 320 movement rows survived but the stored snapshot ended at **58 instead of 320**. This exactly matches the reported pattern: the transaction/entity-derived Stock Check can remain mathematically complete while the stored current-stock snapshot loses increments.

Several independent deterministic paths can also create divergence: return approval/rejection/delete transitions apply stock based on status incorrectly; negative-sale return movements are relinked away from the sale and then missed by sale cancellation/deletion; closing-stock save overwrites live current stock but closing-stock delete cannot find the movement it created; manual stock adjustment and legacy direct-stock endpoints are not represented by the Stock Check formula; and purchase invoice items do not preserve product type.

The working checkout’s local database is schema-only. It contains zero products, sales, purchases, returns, dumps, movements, adjustments, and closing-stock rows, so there is no real transaction history from which to report production mismatch counts. All database queries in this audit were SELECT-only and returned zero because the checkout database is empty. Reproductions were run only against separate temporary databases.

> **Bottom line:** Before any refactor, the system needs an agreed stock authority and a controlled migration/validation plan. The safest first production action is not an automatic repair; it is to stop adding new mutation paths, preserve movement history, and measure the live database with read-only diagnostics.

## 1. How stock is represented today

| Representation | Used by | What it contains | Consistency risk |
|---|---|---|---|
| `regular_products.current_stock` / `non_products.current_stock` | `/api/stock/current`, sales-entry availability, low-stock, closing-stock display | Mutable live snapshot | Can be overwritten, lose concurrent updates, or be changed without a report-visible entity |
| `StockMovement` | Central helper, purchase calculation, audit/debug endpoints | Signed quantity plus previous/new snapshot, movement date, loose reference fields | No database foreign-key or uniqueness protection; old and new references are mixed |
| Sale/SaleItem tables | Stock Check sales component | Positive quantities from finalized sales only | Negative sale lines are excluded and require a separate `CustomerReturn` entity |
| CustomerReturn | Stock Check customer-return component | Completed positive returns only | Backend status handlers do not consistently follow this rule |
| DumpEntry | Stock Check dump component | All dump rows in the date range | No status filter; direct legacy dump endpoint creates no row |
| SupplierReturn | Stock Check supplier-return component | All supplier-return rows in the date range | No status filter; create/approve/reject/delete stock effects are inconsistent |
| ClosingStock | Stock Check opening and actual closing columns | Manual closing quantity by product/date | POST overwrites live stock; delete cannot reverse the created movement |
| Browser `localStorage` holds | Sales-entry availability only | Unsaved invoice lines/reservations in one browser profile | Not server-side, not shared between users/devices, and not a database stock movement |

The core model definitions confirm that product IDs are independent across the regular and non-product tables, while `StockMovement.product_id` is paired with a free-form `product_type`. `PurchaseInvoiceItem.product_id` has no product-type field, and `StockMovement.reference_id`/`reference_type` have no foreign-key or uniqueness constraint.[1] [2]

## 2. Intended flow versus actual implementation

| Flow | Current-stock mutation | Stock Check source | Reversal/edit behavior | Audit result |
|---|---|---|---|---|
| Finalized sale, positive line | `-quantity`, movement `sale`, reference `sale` | Positive finalized `SaleItem.quantity` | Update reconciles movement net by product; delete/cancel reverses only movements still referenced as `sale` | Works in serialized ordinary cases; vulnerable to concurrency and stale/duplicate history |
| Finalized sale, negative line | `+abs(quantity)`, movement initially `sale` then relinked to `customer_return`; completed `CustomerReturn` is created | Positive sale quantity excluded; completed `CustomerReturn` quantity added | Sale update/delete queries only `reference_type='sale'`; relinked return movement is missed | **Critical deterministic deletion/cancellation hole** |
| Purchase invoice | `+quantity`, movement `purchase` | Purchase/purchase-reversal movements | Update reverses every old item then adds every new item; delete reverses every item | Ordinary duplicate lines net correctly; partial-commit and product-type risks remain |
| Standalone completed customer return | `+quantity`, movement `customer_return`, entity row | Completed `CustomerReturn` row | Delete always subtracts quantity | Normal completed create/delete is aligned; status and numeric update paths are not |
| Dump entry | `-quantity`, movement `dump`, `DumpEntry` row | All `DumpEntry` rows | Edit applies quantity difference; delete restores quantity | Ordinary create/edit/delete is aligned when serialized |
| Supplier return through entity route | Create always `-quantity`, movement `supplier_return`; entity row | All `SupplierReturn` rows regardless of status | Approve subtracts again; reject adds once; delete always adds once | **Critical status-dependent double/incorrect application** |
| Manual stock adjustment | `+/-` delta, movement `adjustment`, `StockAdjustment` row | Not included in Stock Check formula | No report component includes it | **High: direct stock changes invisible to Stock Check** |
| Legacy direct customer-return/dump/supplier-return routes | Helper writes a movement but does not create entity row; reference IDs are null or generic | Entity tables, not those movements | No entity reversal path | **High API bypass; not referenced by current frontend** |
| Closing-stock save | Direct assignment `current_stock = submitted quantity`, movement `closing_stock_adjustment` | Manual `ClosingStock` row used as `clStock`; movement excluded from formula | Delete searches by closing row ID, but save stores movement `reference_id=None` | **High: live snapshot overwrite and non-reversible delete** |

The main Stock Check calculation is `opening + purchases - positive finalized sales + completed customer returns - dumps - supplier returns`. Purchases are taken from `StockMovement`; the other categories are primarily reconstructed from entity tables.[3]

## 3. Severity-ranked findings

| ID | Severity | Finding and affected flows | Why the two values diverge | Evidence and proof | Safe remediation direction |
|---|---|---|---|---|---|
| F1 | **Critical** | SQLite concurrent updates lose stock increments. Affects sales, purchases, returns, dumps, supplier returns, adjustments, and closing-related helper calls. | Two requests can read the same old snapshot. Each writes its own `new_stock`; the last write wins, while both movement rows remain. Stock Check reads the surviving transaction rows rather than recomputing the snapshot from the lost writes. | `update_product_stock` uses read-modify-write plus `with_for_update()` at `app.py` lines 626–693; SQLite is configured with `check_same_thread=False` and `isolation_level=None` at lines 76–92. Isolated probe: 320 successful concurrent `+1` calls, 320 movement rows, quantity sum 320, but `current_stock=58`.[4] | Make the stock update atomic at the database level, preferably on a server database with row locking or an atomic conditional SQL increment. Keep movement insertion in the same transaction. Add a concurrency test that asserts snapshot equals ledger after parallel operations. |
| F2 | **Critical** | Customer and supplier return status transitions are not idempotent. | The route logic does not calculate stock effect from old status to new status. Customer pending create does not add, but reject subtracts and delete subtracts again. Supplier create subtracts regardless of status, approve subtracts again, reject adds once, and delete adds regardless of status. | Customer routes: `app.py` lines 8815–9217. Supplier routes: lines 9302–9748. Isolated reproduction: customer pending create 100 → reject 95 → delete 90; supplier pending create/approve produced two `-5` movements; rejected/deleted supplier return left an extra `+4` cancellation.[5] | Define one status-to-stock-effect state machine. Apply only the delta between old effective effect and new effective effect. Deletion should reverse the recorded effective effect, not blindly use quantity. |
| F3 | **Critical** | Negative sale return movements are missed on sale cancel/delete. | Create relinks the positive negative-line movement from `(sale, sale_id)` to `(customer_return, customer_return_id)`. Later sale update/cancel/delete searches only `(reference_type='sale', reference_id=sale.id)`, so the return movement is excluded. The CustomerReturn entity is then deleted, leaving the positive snapshot delta with no report-visible return. | Relinking occurs at `app.py` lines 1042–1117. Status reversal queries only `reference_type='sale'` at lines 1430–1460; delete does the same at lines 1718–1753.[6] | Preserve a sale-line or transaction-line identity on every movement, or include linked customer-return movements when reversing a sale. Do not delete the return entity until its stock effect has been reversed in the same transaction. |
| F4 | **High** | Closing-stock save directly overwrites live stock; delete cannot reverse it. | Saving a manual closing quantity assigns it to `product.current_stock`. The movement is created with `reference_id=None`, but delete searches for `reference_id == closing_stock.id`; it therefore removes the row without restoring the snapshot. Historical closing saves can also reset today’s live stock to an old quantity. | `app.py` lines 7569–7666 assign the snapshot and create a NULL-referenced movement; delete searches by closing ID at lines 7673–7734. Frontend shows live current stock next to closing quantity and allows date selection.[7] | Decide whether closing stock is a physical adjustment or a reporting observation. If adjustment, model it as an explicit effective adjustment with a durable reference and reversible event. If observation, never overwrite live stock. Require an explicit confirmation for historical corrections. |
| F5 | **High** | Stock Check and current snapshot use incompatible event sources and status rules. | An event may update current stock but not the entity table, or appear in an entity table while the mutation route applied the wrong amount. Stock Check counts supplier returns and dumps regardless of status, but customer returns only when completed; manual adjustments are ignored. | Helper functions at `app.py` lines 8188–8314 show purchase movements plus entity-table queries and the status/date filters. The report formula is at lines 7991–8045 and 8064–8121.[3] | Select one authoritative signed event ledger and derive both current stock and Stock Check from it. Keep entity tables as transaction documents, but record one immutable stock-effect event per effective state change. |
| F6 | **High** | Manual adjustment and legacy direct-stock endpoints bypass Stock Check. | `/api/stock/adjust` writes an `adjustment` movement and current snapshot, but Stock Check does not include adjustment movements. Legacy customer-return/dump/supplier-return routes write only a movement and no corresponding entity row, so entity-based report components cannot see them. | Manual adjustment route: `app.py` lines 7383–7454. Legacy routes: lines 8316–8392. Isolated legacy probe returned successful stock values but left no CustomerReturn, DumpEntry, or SupplierReturn rows.[8] | Route all stock-changing operations through a single transaction service that writes a typed event consumed by reporting. Either include manual adjustments in Stock Check explicitly or restrict them to a controlled reconciliation workflow. |
| F7 | **High** | Purchase invoice product identity is ambiguous for regular versus non-product items. | The frontend prefixes the UI selection with `regular-` or `non-`, then stores only numeric `productId`. Backend checks the regular table first. Since the tables have independent ID sequences, regular ID 1 and non-product ID 1 can coexist; a non-product purchase can update the regular product. | Frontend selection/payload: `purchase-invoice.tsx` lines 350–412 and 468–484. Backend type inference: `app.py` lines 6125–6136, 6211–6223, and 6326–6336. Isolated probe: non-product ID 1 increased regular stock 80 → 85 while non-product stock stayed 20.[9] | Persist `product_type` with each purchase item and require it in create/update/delete. Add a composite product identity `(product_type, product_id)` to every transaction and movement path. |
| F8 | **High** | Sale creation can commit a stock movement but continue when negative-sale CustomerReturn creation fails. | The sale’s stock increase for a negative line occurs before the return entity is created. Failure is logged as a warning and does not fail the sale. Stock Check then lacks the completed return row even though current stock increased. | `app.py` lines 1061–1121 explicitly catch and log return-creation failure, followed by the transaction commit at lines 1123–1125.[10] | Make the sale and its negative-line return entities one atomic operation. If the entity cannot be created, roll back the sale’s stock movement and the sale itself. |
| F9 | **Medium–High** | Return and dump pages do not invalidate stock queries after mutations. | The backend may succeed, but an already-open sales-entry or closing-stock page keeps its cached `/api/stock/current` data. Purchase and sale pages do invalidate; return/dump/supplier-return pages only refresh their own lists. | Customer-return create/delete: `return-from-customer.tsx` lines 199–233. Dump create/delete: `dumps.tsx` lines 89–138. Supplier-return create/update/delete: `return-to-supplier.tsx` lines 277–323. Sales/purchase invalidation is present in the corresponding mutation handlers.[11] | Invalidate and refetch `currentStock` and stock-check queries after every stock-affecting mutation. Broadcast a stock event for all transaction types. Treat freshness as a UX concern separate from backend correctness. |
| F10 | **Medium–High** | Holds are local browser reservations, not multi-user stock holds. | New sales subtract unsaved lines and `localStorage.heldInvoices`; edit mode uses a different formula and does not subtract held reservations. Separate users/devices have separate local storage and receive no server reservation. This can cause overselling and stale availability, even when the final Stock Check event totals are correct. | Sales-entry availability formulas: `sales-invoice.tsx` lines 506–560. Hold persistence and auto-hold: lines 1377–1593 and 1955–2192. Browser-only broadcast behavior: `useCrossTabSync.ts` lines 9–44.[12] | If holds must reserve inventory, create server-side reservations with expiry and atomic allocation. Otherwise label them as drafts only and remove their quantity from authoritative availability calculations. |
| F11 | **Medium** | Historical date semantics are inconsistent. | Purchases use `movement_date` with a NULL/created-at fallback; sales and returns use entity dates; historical closing uses latest `created_at` movement; opening stock looks back only seven days and returns zero for a product omitted from an active closing day. Products without a recent closing baseline can have initial stock ignored by production Stock Check. | `get_opening_stock` and helper date filters: `app.py` lines 8145–8314. Historical closing uses `created_at` at lines 7737–7797. Initial stock is stored and initialized at `models.py` lines 192–195 and 256–259.[13] | Define a single business-date policy. Compute opening from the last authoritative balance/event before the period, without a seven-day artificial cutoff. Use business date for reporting and system timestamp only for audit ordering. |
| F12 | **Medium** | Return quantity updates have a reachable Decimal/float failure. | The update route stores old quantity as a database Decimal and new quantity as float, then subtracts them directly. A normal pending return quantity edit can return HTTP 500 before completing its stock/status update. | Customer-return update at `app.py` lines 8959–8997; isolated route reproduction returned `unsupported operand type(s) for -: 'float' and 'decimal.Decimal'`.[5] Supplier-return update has the same pattern at lines 9487–9525. | Normalize quantities to Decimal or float consistently before comparison and arithmetic. Add route tests for quantity changes, product changes, status changes, and date changes. |
| F13 | **Medium** | Purchase invoice creation commits the header before item and stock processing. | If a later product lookup or stock update fails, rollback cannot undo the already committed invoice header. This can leave an invoice without complete items/movements, while the report sees only whatever rows succeeded. | `create_purchase_invoice` commits the header at `app.py` lines 6103–6110, then processes items and stock at lines 6112–6157.[14] | Create header, items, and stock movements in one transaction; commit once after all validation and writes succeed. |

## 4. Invoice edits and duplicate product lines

The sale update code correctly attempts to aggregate duplicate sale lines by `(product_id, non_product_id)` and derive a target signed effect. In the isolated test harness, repeated product lines and repeated edits passed the intended ledger-based checks. This is a meaningful improvement over a simple “one movement per visible row” implementation.

However, the reconciliation remains fragile because it searches only sale-referenced movements, while negative-line movements may have been relinked to CustomerReturn. It also deletes and recreates CustomerReturn entities before reconciling the movement set. Any older data created under a previous reference convention can therefore be invisible to the update’s current query. The delete/cancel behavior has the same reference-scope problem. The application has no database uniqueness constraint that would prevent duplicate movement rows; correctness depends on application cleanup and reconciliation logic.[15]

Purchase invoice duplicate lines are not aggregated, but in a serialized normal case the backend adds each line and later reverses each line, so the net quantity is correct. The more serious purchase issue is that purchase items do not preserve product type, and that the invoice header is committed before item processing.

## 5. Frontend audit conclusions

The frontend does not directly authoritatively write stock; it calls backend APIs. The sales page reads `/api/stock/current` and locally subtracts current invoice quantities and browser-local holds. In edit mode it adds back the original saved quantity, but it does not subtract held-invoice reservations. This means two users can see different availability for the same product, and one user can oversell based on another user’s unseen draft or hold.

The sales and purchase pages perform broad React Query invalidations and browser-tab broadcasts. Customer-return, dump, and supplier-return pages do not refresh the current-stock or Stock Check caches after mutations. This causes a user-visible stale-stock problem even when backend data is correct. It is separate from, but can mask, the deeper backend snapshot/report divergence.

Closing Stock uses `/api/stock/current` as the displayed “Current Stock” value and seeds today’s editable closing quantity from it. The selected closing date is business-date-driven initially, but the frontend’s “is current date” default check uses the calendar date. When business date and calendar date differ, the page can display a historical date while applying different initialization behavior.[7]

## 6. Database evidence status

The local checkout database at `backend/instance/salesmaster.db` is **schema-only**: 0 rows in products, sales, sale items, purchases, purchase invoices, purchase items, stock movements, stock adjustments, dumps, customer returns, supplier returns, and closing stock. Therefore the following are not available from this checkout: real production discrepancy counts, product-specific mismatch examples, duplicate movement counts, actual end-of-day patterns, or user-by-user concurrency incidents.

The read-only integrity query file was still prepared and executed. All anomaly counts were zero solely because the tables are empty. The raw schema/count output is attached separately as `stock-audit-schema.txt`, and the raw integrity output as `stock-audit-integrity.txt`.

## 7. Recommended remediation sequence for discussion

| Stage | Recommendation | Why it should come first |
|---|---|---|
| 0. Preserve and measure | Run the read-only audit queries against a copy or read replica of the real production database. Export only product IDs/types, counts, signed totals, movement-reference anomalies, and date ranges. Do not auto-repair. | The checkout has no business data, so production evidence is still required before choosing a migration strategy. |
| 1. Contain new divergence | Temporarily disable or restrict legacy direct-stock endpoints, manual adjustment writes, and historical closing overrides unless explicitly authorized. Make all return status transitions use one documented rule. | Prevents the mismatch population from growing while preserving current behavior for ordinary transactions. |
| 2. Fix transaction atomicity | Move all stock-affecting header/item/entity writes into one transaction; remove early commits; make negative-sale return creation mandatory. | Prevents partial records and invisible stock movements. |
| 3. Fix concurrency | Use a database-supported atomic increment/row lock, or migrate the write path to a server database with real row locking. Add parallel mutation tests. | This is the directly reproduced critical cause of lost current-stock units. |
| 4. Establish one authoritative event model | Give every stock effect a stable transaction-line identity, signed delta, effective status, business date, and reversal relation. Derive both current stock and Stock Check from the same event set. | Eliminates source and status asymmetry. |
| 5. Reconcile legacy data | After the live read-only report is reviewed, classify mismatches into lost snapshots, double-applied returns, stale closing overrides, bypass movements, product-type collisions, and orphan references. Produce a proposed repair ledger for approval before applying anything. | A repair should be explainable per product and per event, not a blind overwrite. |
| 6. Add regression coverage and monitoring | Test duplicate lines, repeated edits, negative lines, return status transitions, delete/cancel, backdated transactions, concurrent users, and closing deletion. Add a scheduled read-only discrepancy report and alert threshold. | Keeps the two views aligned after remediation. |

## 8. Validation plan after approval

Validation should begin with isolated tests and a staging copy. For every stock-affecting operation, assert that the authoritative event sum, stored current stock, and Stock Check result agree for the same product/type and date range. The test matrix should include one product repeated on at least six invoice lines, multiple edits that change quantity and product, negative lines mixed with positive lines, delete/cancel after negative lines, pending/approved/rejected/completed returns, closing save/edit/delete, manual adjustment, backdated movement, and parallel requests from multiple sessions.

For production, first run a read-only snapshot report before any code or data change. After an approved migration, compare pre/post product balances, movement counts, and transaction totals, and retain a repair log for every changed product. No repair should be inferred solely from the current snapshot because the concurrency reproduction demonstrates that the snapshot can be wrong while movement rows remain intact.
